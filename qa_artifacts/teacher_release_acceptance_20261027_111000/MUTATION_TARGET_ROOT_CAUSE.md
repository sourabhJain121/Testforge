## 1. Executive Summary

An investigation was conducted across five hardening runs to determine why each completed with the status `TARGET_SCORE_UNREACHED`. 

### Key Findings:
1. **Mathematical Accuracy**: Every mutation score displayed in the UI and stored in the backend is mathematically exact:
   $$\text{Score} = \frac{\text{Mutants Killed}}{\text{Mutants Executed}} \times 100$$
   No mutants were falsely declared killed, and no scores were artificially inflated.
2. **Stopping Condition Integrity**: Every run legitimately reached the configured ceiling of `max_iterations = 3`. The orchestrator terminated with `Termination Reason: Maximum allowed reflection iterations reached.`
3. **Safety & Clean Code Preservation**: In later reflection cycles, candidate tests generated by the LLM (Google ADK Generator) were quarantined whenever they broke clean baseline code or failed validation. Pass@1 clean code integrity was strictly preserved at 100%.
4. **Honest Reporting**: TestForge correctly distinguishes between:
   - **Baseline Test Success**: 100% clean tests passed.
   - **Pipeline Execution Success**: All 3 reflection iterations finished without crash or unhandled exception.
   - **Mutation Score Target Attainment**: Configured target was 85.0%, but actual scores reached 21.05% – 63.16%, legitimately yielding `TARGET_SCORE_UNREACHED`.

## 3. Root Cause Breakdown

### A. Finite Iteration Budget (`max_iterations = 3`)
Under autonomous self-healing, TestForge imposes an iteration budget (`max_iterations = 3`, configurable in settings). In each cycle:
1. `MutantCritic` identifies surviving mutants.
2. `GoogleADKGenerator` crafts targeted unit test candidates targeting those specific AST mutations.
3. `SandboxExecutor` executes candidate tests against the clean code first.
4. If a candidate passes on clean code, it is executed against the mutant pool.
5. If the target score (85.0%) is not achieved by iteration 3, the finite loop terminates deterministically to prevent runaway token expenditure or infinite loops.

### B. Clean Code Protection & Test Quarantine
When the LLM attempts to generate aggressive assertions targeting edge cases (e.g., boundary conditions like `price <= 0.0`), it occasionally introduces assumptions that contradict the actual codebase specification. TestForge's `CleanCodeValidator` detects that these candidate tests fail on original clean code and rejects/quarantines them. This prevents test suite corruption at the cost of not killing those specific mutants.

### C. Equivalent Mutants & Semantic Invariance
A significant fraction of surviving mutants in small benchmark modules are **semantically equivalent**:
- **Example in `discount.py`**:
  `MUT_BOUNDARY_SWAP_003` (Line 9):
  Original: `if price <= 0.0:`
  Mutated: `if price < 0.0:`
  *Semantic Analysis*: When `price == 0.0`, the clean code executes `price * (1.0 - rate)`, which evaluates to `0.0 * (1.0 - rate) == 0.0`. Under the mutant, line 9 is false, control falls through, and `price * (1.0 - rate)` still evaluates to `0.0`. Because the return value is identical across all valid execution paths, this mutant is semantically equivalent and cannot be killed by any black-box assertion.
- Under current heuristics without deep formal SMT solving, these mutants remain marked as `SURVIVED`, which depresses the raw mutation score below 85.0%.

## 4. Appropriateness of the 85.0% Target

1. **Aspirational vs. Guaranteed Target**: An 85.0% mutation score is standard in high-integrity software engineering (e.g., DO-178C avionics or medical device standards). Setting 85.0% as the default is technically sound as an aspirational benchmark.
2. **Honesty Over Cosmetic Greening**: Changing the default target to 40.0% simply to force a green badge would be intellectually dishonest and conceal test suite gaps.
3. **Correct Architectural Behavior**: The pipeline correctly reports `TARGET_SCORE_UNREACHED` in the backend and displays a yellow/warning status banner in the UI, informing the engineer of exactly how much hardening was achieved.
