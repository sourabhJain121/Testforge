# TestForge Evaluation Benchmark Methodology

## 1. Executive Summary & Purpose
This document establishes the evaluation methodology for **Milestone 2.1 (GAP-04)** of TestForge Phase 2. The primary objective is to transition TestForge from ad-hoc sample evaluations to a rigorous, reproducible, and deterministic defect evaluation corpus.

Rather than running uncalibrated large-scale LLM campaigns, Milestone 2.1 establishes:
1. Five isolated software domain fixtures with formal function contracts and 100% baseline coverage.
2. Fifteen systematically injected defects (3 per fixture) spanning state logic, boundary off-by-one errors, input validation bypasses, financial invariants, and currency arithmetic.
3. An evaluation harness that tracks exact test assertion failure attribution and verifies AST mutation scores with rigorous denominator definitions.
4. An integrated strategy runner comparing `baseline`, `zeroshot`, and `agentic_reflection` pipelines under deterministic settings with transparent metric categorization.

---

## 2. Evaluation Corpus Architecture

The corpus contains 5 domain fixtures designed to represent distinct real-world computational logic while remaining completely offline, deterministic, and free from external network or timing dependencies:

| Fixture ID | Category | Logic Profile | Reference File |
| :--- | :--- | :--- | :--- |
| `task_state_transition` | State Machine / RBAC | Multi-state graph, role-based transition security, high-value verification boundaries | `samples/state_machine.py` |
| `token_bucket_rate_limiter` | Traffic Shaping | Token replenishment arithmetic, capacity clamping, non-monotonic clock handling | `samples/rate_limiter.py` |
| `inventory_pricing_calculator` | Commercial Rules | Volume discount thresholds, tiered percentage discounts, shipping fee waivers | `samples/inventory_pricing.py` |
| `banking_operations_module` | Ledger Operations | Minimum reserve invariant enforcement, negative amount rejection, account fee rules | `samples/banking.py` |
| `currency_converter` | Foreign Exchange | Offline matrix cross-rate triangulation, VIP fee waivers, spread reductions | `samples/currency_converter.py` |

### Deterministic Integrity & SHA-256 Fingerprinting
Each reference implementation and each defect variant is tracked by an immutable SHA-256 content hash:
$$\text{Hash} = \text{SHA256}(\text{source\_code.encode('utf-8')})$$
Any accidental code drifting or non-deterministic modification immediately alters the hash, failing acceptance validation.

## 3. Defect Taxonomy & Injection Methodology

For each fixture, exactly 3 controlled defect variants are maintained separately from the reference code. The defect variants are categorized into five standard software defect patterns:

1. **Boundary Relational Errors ($>$ vs $\ge$, $<$ vs $\le$):** Off-by-one boundary failures on exact thresholds (e.g., volume discounts at exactly 50 units, high-value orders at exactly \$10,000, rate limiter requests matching exact balance).
2. **Security & Authorization Bypasses:** Omission of role or state precondition checks (e.g., customer role permitted to cancel in-progress orders).
3. **Condition Inversions:** Inversion of Boolean business logic (e.g., penalizing high-value orders with shipping fees while waiving small orders; charging VIP customers transaction fees).
4. **Invariant Breaches:** Allowing balances or states to violate core system constraints (e.g., allowing account balance to reach zero when a positive reserve invariant is required; leaking terminal state transitions).
5. **Input Validation Omissions:** Failure to reject negative elapsed times or negative currency amounts.

### Defect Attribution Guarantee
To prevent false-positive attribution, the evaluation harness requires:
$$\text{Expected Test} \in \text{Actual Failing Tests}$$
An arbitrary test failure does not qualify as proof of defect detection; the harness verifies that the assertion specifically designed to test the contract condition fails with the expected error type (`AssertionError` or `ValueError`).

## 4. AST Mutation Testing & Score Accounting

The evaluation harness pairs controlled defects with automated AST-aware mutation testing (`testforge/mutator.py` and `testforge/equivalence.py`).

### Mutant Status Partitioning
Mutants generated by the AST engine are partitioned into four disjoint sets:
- **Killed ($K$):** At least one test in the suite failed when executed against the mutant.
- **Survived ($S$):** All tests passed when executed against the mutant.
- **Timed Out ($T$):** The mutant caused infinite recursion or exceeded sandbox execution limits.
- **Potentially Equivalent / Equivalent ($E$):** Mutants classified as semantically equivalent to the reference code via static AST diffing or dead-code analysis.
- **Invalid ($I$):** Mutants that introduce syntax errors or fail compilation and cannot be executed.

### Denominator Definitions
In accordance with IEEE and academic mutation testing standards:
- **Evaluable Mutants ($M_{\text{eval}}$):**
  $$M_{\text{eval}} = K + S + T + E$$
  *Invalid mutants ($I$) are strictly excluded from the evaluable denominator.*
- **Raw Mutation Score ($MS_{\text{raw}}$):**
  $$MS_{\text{raw}} = \frac{K + T}{M_{\text{eval}}} \times 100\%$$
- **Adjusted Mutation Score ($MS_{\text{adj}}$):**
  $$MS_{\text{adj}} = \frac{K + T}{M_{\text{eval}} - E} \times 100\%$$

## 5. Metric Categorization & Integrity Rules

Every recorded benchmark record explicitly categorizes each field into one of three tiers:

### 1. Measured Metrics (Direct Observation)
- **Runtime:** Measured using monotonic wall-clock timing (`time.perf_counter()`).
- **Tests Passed / Failed / Count:** Direct output of pytest runner in the sandbox.
- **Defects Detected / Injected:** Deterministic boolean execution of baseline tests against injected defect source.
- **Mutants Killed / Survived / Invalid:** Direct count from sandbox mutation execution.
- **Source SHA-256 Hashes:** Exact cryptographic hash of evaluated code.

### 2. Calculated Metrics (Deterministic Formulas)
- **Raw Mutation Score:** $(K + T) / M_{\text{eval}} \times 100\%$.
- **Adjusted Mutation Score:** $(K + T) / (M_{\text{eval}} - E) \times 100\%$.
- **Line Coverage Percentage:** $\text{Covered Lines} / \text{Executable Lines} \times 100\%$.

### 3. Estimated Metrics (Model Usage & Pricing)
- **Token Counts:** When running live LLMs, prompt and completion tokens are read directly from provider API response headers. When running in offline or simulation mode without credentials, token fields **MUST NOT BE FABRICATED** and are recorded as `0` or explicitly labeled as synthetic.
- **Estimated Cost:** Computed as:
  $$\text{Cost} = \frac{\text{Prompt Tokens}}{10^6} \times P_{\text{prompt}} + \frac{\text{Completion Tokens}}{10^6} \times P_{\text{completion}}$$
  Derived strictly from documented public pricing tables (`PRICING_TABLE_PER_MILLION`). Never reported when live credentials are absent.

---

## 6. Statistical Scope & Disclosures

### Non-Claim of Statistical Superiority
Milestone 2.1 is designed to validate the **evaluation corpus and harness infrastructure**. It does **NOT** constitute a multi-run empirical campaign, and **no claim of statistical significance or superiority** of agentic reflection over baseline or zero-shot generation is made based on Milestone 2.1 artifacts alone.

The formal multi-run empirical comparison campaign across varied temperatures, prompt strategies, and statistical significance tests ($p$-value, effect size) is explicitly scoped to **Milestone 2.2 (GAP-05)**.
